# BlinkLinks: self-hosted links reference, v0.1.1

Only link navigation is in scope: canonical HTTPS deep links, web/store fallback, associated-domain metadata examples and portable Android referrer encoding and parsing. The MIT license applies only to this repository. No Bridgee account, SDK, private core, paid attribution, tracking, hosted deployment or service is included. No dependencies, credentials, actual application IDs or certificates are provided.

## Run locally, no account or install
Use Node 20+; run `npm test`, then `npm start`. Open http://127.0.0.1:8789/ → **Try link /p/42**. The fallback page provides dummy web/store targets; do not use those apps. The developer example validates the route and fixtures; nothing is deployed.

## Self-host on infrastructure you own (recommended)

1. Copy `static.example.json` to your local config file. Set `linkHost` to your dedicated HTTPS origin and `webHost` to the customer's own web origin. Replace all dummy app identifiers and the SHA-256 digest with the public identifiers of the actual distributed builds; the iOS Team ID is ten characters. Do not supply a signing key, customer data or secrets. Set `productIds` to the public numeric destinations you want to build. The example uses reserved domains and is not deployable as-is.
2. Run `node static.mjs YOUR_CONFIG.json NEW_OUTPUT_DIRECTORY`. The directory must not already exist. Publish **only that directory's contents**, including the hidden `.well-known` directory, to a static HTTPS host operated by the customer. No Node process, API, lease, AWS account or Bridgee connection is needed at runtime. The generated pages have no JavaScript, trackers, cookies or third-party resource loads; the visitor chooses whether to follow the web/Google Play/App Store links. The customer is responsible for their domain, hosting plan and its costs.
3. The link is `https://YOUR_LINK_HOST/p/42.html`, not the customer website product URL. Configure the origin to serve routes verbatim (no pretty-URL, SPA fallback, authentication or CDN redirects for association files). Check both `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` return **HTTP 200**, valid JSON, `application/json`, and no 3xx response over public HTTPS. The emitted conventional `_headers` file is understood only by some hosts; otherwise configure those MIME types on your host. Check the real item route and web/store links with cookies disabled.
4. Add the same HTTPS host and path in the signed apps; the app must implement navigation and validate the incoming route (see below). On Android, pass the returned referrer into the app-side rule with that exact trusted customer origin. Confirm on signed physical devices, both without and with the app, then through a real Google Play installation. On iOS, after App Store install the person manually reopens the original link from the original message/QR or another app; Safari can keep same-domain taps in the browser, so the fallback page gives instructions instead of a same-page button. [Apple TN3155](https://developer.apple.com/documentation/technotes/tn3155-debugging-universal-links). No automatic App Store handoff is offered.

Static files can change via regenerate/redeploy and cache invalidation. There is no live editing API, device-sniffed redirect, link management service, install attribution, QR generator or analytics. A static browser fallback offers explicit alternatives rather than inferring what app is installed. If a customer needs dynamic routes, operate their own service on their infrastructure and validate it separately; the loopback fixture is not a production server. No change to the separate paid Bridgee Marketing Channel is implied.

## Integrate a real app
- iOS installed: publish your AASA directly on your HTTPS link host, add the corresponding Associated Domains entitlement, and handle the delivered browsing-web activity in your app. Apply the allowlisted route rule before navigating. [Apple Associated Domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains).
- Android installed: publish your assetlinks JSON directly on the HTTPS link host with the **distributed** app signing certificate digest; add the verified HTTPS App Link intent filter to your host app and validate the incoming URI before navigating. [Android App Links](https://developer.android.com/training/app-links).
- Android deferred through Google Play: the Play URL nests one `blink_link` parameter inside `referrer`. Your host app must integrate Google's Play Install Referrer client and feed the returned string to equivalent allowlisted parsing before navigating. Treat a referrer as an untrusted routing hint, not identity, entitlement or attribution. Persist consumption if needed and make app-side navigation idempotent. Unsupported/unavailable/malformed referrer means default navigation. Sideloads and other stores are not supported by this mechanism. [Google Play Install Referrer](https://developer.android.com/google/play/installreferrer).
- iOS after App Store: return to the original link and reopen it explicitly after install. There is no automatic deferred handoff, fingerprinting or clipboard read in this candidate.

These are association examples and portable reference rules, not a signed host app or native install integration test. Before claiming production platform support: test exact HTTPS host and signed build on physical iOS and Android; cover installed, absent/fallback and post-store scenarios independently. Do not expose the loopback fixture as a production service.
